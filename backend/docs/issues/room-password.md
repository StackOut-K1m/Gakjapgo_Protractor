# 잠긴 방이 안 잠긴다 — 입장 시 비밀번호 검증 없음

| | |
|---|---|
| 영역 | 스터디룸 (BE) |
| 심각도 | 높음 — 기능이 이름뿐이었다 |
| 발견 | 2026-08-03, `fix/study-room-create-edit` 머지 직후 코드 확인 중 |
| 상태 | ✅ 수정 완료 (테스트 8건 통과) |

## 무엇이 문제였나

비공개 방 기능이 프론트에만 있었다. `JoinRoomRequest`에 `password` 필드는 있는데
`StudyRoomService.join()`이 그 값을 **한 번도 읽지 않았다.**

프론트의 `roomPassword.ts`는 잘 만들어져 있었다. 팝업으로 열리는 준비 화면에 비밀번호를
넘기려고 쿼리스트링·sessionStorage·postMessage를 검토하고 `window.opener`를 고른 근거까지
주석에 남아 있다. 다만 그것은 **값을 전달하는 문제**를 푼 것이지 **검증**이 아니다.

프론트 API 파일에도 이미 경고가 적혀 있었다.

```
⚠️ password 는 잠긴 방일 때 보낸다. 다만 서버가 아직 이 값을 검사하지 않는다.
   검증이 붙기 전까지는 틀린 비밀번호로도, 아예 보내지 않아도 입장이 성공한다.
```

### 재현

Swagger나 curl로 입장 API를 직접 부르면 비밀번호 화면을 거치지 않는다.

```bash
curl -X POST /api/v1/study-rooms/{roomId}/join \
  -H "Authorization: Bearer <아무 회원 토큰>" \
  -d '{"cameraChecked":true,"postureChecked":true}'
```

비밀번호를 넣지 않아도 200이 떨어지고 방에 들어간다.

### 왜 이런 일이 생겼나

**화면에서 막는 것과 서버에서 막는 것을 같은 일로 본 것**이 원인이다. 화면 흐름은 사용자를
안내하는 장치고, 실제 권한은 API가 지켜야 한다. 프론트를 거치지 않는 경로가 항상 존재한다.

곁들여 발견한 것: `password`가 **평문으로 저장**되고 있었다. DB가 새면 그대로 노출된다.

## 어떻게 고쳤나

### 1. 입장 시 비밀번호 대조 → 틀리면 403

`StudyRoomService.join()`에서 정원 확인보다 **먼저** 본다. 들어올 자격이 없는 사람에게
방에 몇 명 있는지 알려 줄 이유가 없다.

### 2. 재입장은 통과시킨다

이미 방에 있는 회원(`left_at IS NULL`)에게는 묻지 않는다. 입장 API는 **준비 화면과
스터디룸에서 두 번 불리고, 새로고침으로도 다시 불린다.** 매번 비밀번호를 요구하면 정상 입장이
중간에 막힌다. 정원 확인이 이미 같은 이유로 같은 조건을 쓰고 있어서 그 자리에 넣었다.

### 3. 비밀번호 해싱 (BCrypt)

회원 비밀번호와 **같은 인코더**를 쓴다. `SecurityConfig`에 `BCryptPasswordEncoder` 빈이
이미 있어서 주입만 했다. 저장은 `encode`, 대조는 `matches`다.

`matches(null, ...)`는 `IllegalArgumentException`을 던지므로 null·빈 값을 먼저 거른다.

### 4. 잠근 방에 비밀번호가 없으면 400

`isLocked=true`인데 `password`가 비면 개설·수정에서 막는다.

이 조합이 만들어지면 입장에서 **대조할 값이 없어진다.** 통과시키면 잠금이 이름뿐이고, 막으면
방장이 자기 방에 못 들어간다. 어느 쪽도 답이 아니라서 애초에 생기지 않게 했다.

수정(PATCH)은 `isLocked`만 켜고 비밀번호를 안 보낼 수 있다. 합쳐진 결과를 봐야 알 수 있어
`room.update(...)` **뒤에** 확인한다. 여기서 던지면 트랜잭션이 되돌아가므로 잘못된 상태가
저장되지 않는다.

### 로그

비밀번호 불일치는 `log.info`로 남긴다. **입력값은 남기지 않는다** — 로그에 비밀번호가 그대로
쌓인다. 방 id만 남긴다.

`isLocked`인데 저장된 비밀번호가 없는 방은 `log.error` + 500이다. 개설·수정에서 막고 있으므로
이 로그가 찍히면 그 이전에 만들어진 데이터라는 뜻이다.

## 테스트

인코더는 목이 아니라 **진짜 `BCryptPasswordEncoder`**를 쓴다. 저장할 때 해싱하고 대조할 때
푸는 왕복이 실제로 맞물리는지가 핵심이기 때문이다.

| 경우 | 기대 |
|---|---|
| 잠긴 방 + 맞는 비밀번호 | 입장 성공 |
| 잠긴 방 + 틀린 비밀번호 | 403, **입장 기록을 만들지 않음** |
| 잠긴 방 + 비밀번호 미전송 | 403 (예전엔 이대로 통과했다) |
| 잠긴 방 + 저장된 비밀번호 없음 | 500 (통과시키지 않음) |
| 공개 방 | 비밀번호 없이 입장 |
| 이미 방에 있는 회원 | 다시 묻지 않음 |
| 개설: 잠금 + 비밀번호 없음 | 400, 저장 안 됨 |
| 개설: 비밀번호 저장 | 평문이 아니고 `matches`가 참 |

## ⚠️ 배포 시 주의 — 기존 잠긴 방은 못 들어간다

해싱을 켜면 **DB에 평문으로 남아 있는 기존 비밀번호와는 대조가 안 된다.** BCrypt가 평문을
해시로 인식하지 못해 항상 불일치가 된다.

방은 수명이 짧아서(개설 후 10분 · 빈 방 30초) 실사용에는 영향이 거의 없다. 그래도 배포 시점에
남아 있는 잠긴 방은 정리하는 편이 낫다.

```sql
-- 배포 전 확인
SELECT study_room_id, title FROM study_rooms
WHERE is_locked = 1 AND deleted_at IS NULL;

-- 남아 있으면 잠금 해제 (비밀번호를 모르므로 되살릴 방법이 없다)
UPDATE study_rooms SET is_locked = 0, password = NULL
WHERE is_locked = 1 AND deleted_at IS NULL;
```

## 남은 것

- **`GET /study-rooms/{roomId}/preparation`은 잠긴 방도 그냥 보여준다.** 제목과 현재 인원
  정도라 민감하진 않지만, 목록에서 이미 보이는 정보인지 확인이 필요하다.
- 비밀번호 형식 제약이 없다. 현재 `@Size(max = 255)`뿐이라 한 글자도 통과한다. 프론트가
  숫자 4자리로 받고 있다면 서버도 같은 조건을 거는 편이 낫다.
