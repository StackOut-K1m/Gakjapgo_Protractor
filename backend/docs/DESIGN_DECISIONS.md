## 결정 1. DB 스키마 정본 — ✅ 확정
- **정본: `잡다한 명세서/정상적인거/protractor_init_schema.sql`** (study_rooms / study_records / events, 15테이블)

## 결정 2. 세션 통계 계산 위치 — ✅ 확정 (하이브리드)
문서 상충(v4=서버계산 / csv=클라 누적값)을 아래로 정리. **각 데이터 출처에 따라 분리.**

| study_records 컬럼 | 채우는 방식 | 담당 |
|--------------------|------------|------|
| focused_seconds, break_seconds, away_seconds | 클라가 측정 → `progress`로 주기 전송 → 서버 저장 | 측정=클라 / 저장=BE |
| total_study_seconds | 서버가 progress 수신 시 = focused+break+away 로 산출 | BE |
| bad_posture_seconds, warning_count, stretching_attempt/completed_count | 서버가 `events` 테이블 집계 | BE |
| good_posture_ratio, focus_score, neck/shoulder/shoulder_tilt_score, total_score | 서버가 `end`에서 계산 후 저장 | BE |

> 구현 시 정정: 부위 점수는 `neck/shoulder/back`이 아니라 **`neck/shoulder/shoulder_tilt`**다. 감지 3종이 거북목·라운드숄더·어깨 높낮이이고, 뒤 둘은 `body_part`가 모두 SHOULDER라 `detail`로 구분한다.
>
> 재정정(감지 개편 후): 라운드숄더는 판정에서 빠지고 **턱 괴기(CHIN_REST)**가 그 자리를 이어받았다. 처음에는 `shoulder_score` 컬럼을 그대로 재사용했으나 이름과 내용이 달라 `chin_rest_score`로 바꿨다(20260805_08 마이그레이션). 감지 3종 = 거북목·어깨 높낮이·턱 괴기 — 거북목·턱 괴기가 둘 다 NECK이라 여전히 `detail`로 구분한다.

**핵심 원칙:** 점수·자세 지표는 **클라가 보낸 값을 신뢰하지 않고 서버가 `events`로 재계산**한다(치팅·랭킹 무결성).
- 근거: 기능명세 v4 FR-SESS-05 "클라이언트 자기신고 금지".
- 기존 csv의 "서버는 누적값만 저장"은 **focused/break/away 측정값에 한해** 유효(점수는 예외).
- 점수 공식(가중치·감점 기준)은 별도 TBD — AI 정확도 테스트(FR-AI-06/07) 후 파라미터 확정. **계산 위치(서버 end)만 이번에 확정.**

## 결정 3. 타이머 API 방식 — ✅ 확정 (2종 분리)
문서 상충(v4=개인 start/pause/resume/end 개별 API / csv=progress 대체)을 아래로 정리.

| 타이머 | 방식 | 저장 |
|--------|------|------|
| 개인 학습 타이머 (focused/break/away) | **클라 로컬 카운트 + `PATCH /study-records/{id}/progress` 30초 주기 동기화** | study_records |
| 방 공용 페이즈 (집중→스트레칭→휴식) | **서버 관리 + WebSocket 브로드캐스트**, 재입장 시 현재 페이즈 동기화 | 서버 메모리 |

- 개인 타이머 개별 API(`start/pause/resume/end`)는 **채택 안 함** — 왕복 과다·크래시 취약.
- 방 페이즈는 v4대로 서버 관리 유지.
- 세션 종료는 `PATCH /study-records/{id}/end` 로 확정(점수 계산 트리거).

> 구현 시 정정 2건.
> ① 리소스명을 테이블과 맞춰 `study-sessions` → **`study-records`** 로 변경했다.
> ② 방 페이즈 진행 상태는 `study_room_phase_records`가 아니라 **서버 메모리**에 둔다. 초 단위로 변하는 값이라 DB에 쓸 이유가 없고, 재입장 동기화는 `GET /study-rooms/{id}/timer/state` 로 해결된다. 페이즈 이력을 남길 필요가 생기면 그때 테이블을 쓴다.

## 결정 6. 실시간 상태 저장 위치 — ✅ 확정 (서버 메모리)
접속 여부·미디어 상태·최근 채팅·타이머 진행을 Redis가 아닌 **서버 메모리**(`ConcurrentHashMap`)에 둔다.

- 근거: **다중 서버로 확장하지 않기로 팀이 결정**했다. 단일 서버에서 Redis를 거치면 왕복만 늘고 얻는 게 없다.
- 대가: 서버를 재시작하면 채팅 기록·미디어 상태가 비고 방 타이머가 멈춘다. **시연 중 배포 금지**로 관리한다.
- 서버가 여러 대가 되면 이 세 가지를 Redis로 옮겨야 한다. 그때 바꿀 지점: `RoomPresenceTracker`, `MediaStateService`, `ChatHistoryService`, `StudyRoomTimerService`.
- 채팅은 **최근 50건**만 보관한다. 새로고침 후 대화를 이어 보여주는 것이 목적이지 이력 보존이 아니다.

## 결정 7. 이탈 처리 — ✅ 확정·구현 완료 (WebSocket 연결 + 20초 유예)
"나가기 버튼을 눌렀는가"가 아니라 **"WebSocket이 붙어 있는가"** 로 접속을 판단한다.

- 근거: 나가기 버튼을 얌전히 누르는 경우가 오히려 드물다. X로 닫기·강제 종료·네트워크 끊김에서도 같은 결과가 나와야 참여자 목록과 공부 기록이 맞는다.
- **20초 유예**: 서버는 강제 종료와 새로고침을 구분할 수 없다. 둘 다 WebSocket이 끊길 뿐이다. 유예가 없으면 F5가 퇴장이 된다.
  - 처음 15초로 잡았다가 **20초로 늘렸다.** 새로고침 후 복귀에는 페이지 로드·JWT·WebSocket 재연결만이 아니라 **OpenVidu 재연결과 MediaPipe 모델 재로딩**이 들어간다. 측정된 프레임 stall이 p95 2.7초였고 초기 모델 로딩은 그보다 길다. 15초면 느린 PC에서 새로고침이 퇴장으로 처리되어, 유예를 둔 목적 자체를 못 지킨다.
- 유예가 실제로 의미를 갖는 것은 **방에 혼자 있을 때뿐**이다. 2명 이상이면 한 명이 끊겨도 방 상태(RUNNING)는 그대로다. 마지막 한 명이 끊길 때만 방이 ENDED로 넘어가므로, 그 판단을 미루는 시간이다.
- 유예를 넘기면 서버가 **마지막 `progress` 값을 확정값으로 삼아** 세션을 종료한다(`endReason=DISCONNECTED`). 클라이언트 없이도 점수가 계산된다.
- 공부 시간 유실 범위: 정상 종료·X 닫기는 사실상 0(`pagehide` + `keepalive`로 마지막에 한 번 더 전송), 강제 종료·정전은 **최대 30초**(progress 주기).

### 끊겼을 때 실제로 바뀌는 값

| | 유예 안에 복귀(새로고침) | 유예 초과(강제 종료) |
|---|---|---|
| `left_at` · `end_reason` | 변화 없음 | 기록됨 / `DISCONNECTED` |
| 점수 컬럼 | 변화 없음 | 계산됨 |
| `focused_seconds` | 마지막 저장값 유지 | 마지막 저장값으로 확정 |
| `study_rooms.status` | 변화 없음 | 혼자였으면 `ENDED` |
| `joined_at` | **갱신됨** (재입장 API를 다시 부름) | — |

`joined_at`이 새로고침마다 갱신되므로 **"언제부터 공부했나"를 이 값으로 계산하면 안 된다.** 총량은 항상 `focused_seconds`를 본다(랭킹·통계 공통).

## 결정 8. 같은 계정의 중복 접속 — ✅ 확정 (먼저 있던 세션을 종료)
같은 회원이 다른 탭·기기에서 같은 방에 들어오면, **먼저 접속해 있던 세션에만** `/user/queue/session-evicted`를 보내 내보낸다.

- 근거: 화면이 둘이면 카메라와 자세 판정이 이중으로 돌아 감지 결과가 오염되고, 참여자 목록에 같은 사람이 두 번 보인다.

## 결정 9. 방 생명주기와 시간 구분 — ✅ 확정 (백엔드 구현 완료 · 프론트 대기)

> **백엔드 7건은 구현·검증을 마쳤다**(브랜치 `feature/room-lifecycle`, 검증 결과는 9-6-2). 프론트는 팀원 작업이 끝난 뒤 한 번에 붙인다. 시간 3갈래(9-4)에서 "휴식"은 방 타이머 연동이 프론트에 붙어야 완성된다.

### 9-1. 방 상태는 인원 수로 정한다

`study_rooms.status`는 예전에는 생성 시 `WAITING`으로 넣고 그 뒤로 관리되지 않았다. 아래 기준으로 쓴다.

| 상태 | 의미 |
|---|---|
| `WAITING` | 방이 만들어졌고 아직 입장 0명. 방장이 준비 화면(얼굴 인식)에 있는 구간 |
| `RUNNING` | 1명 이상 |
| `ENDED` | 쓰이다가 0명이 됨 |

`WAITING`과 `ENDED`는 둘 다 0명이지만 **한 번도 시작 안 함 / 시작했다 끝남**으로 구분된다(`started_at` 유무와 일치).

**카메라를 꺼도 인원에는 포함된다.** 자리를 비우는 것과 방을 나가는 것은 다르다.

### 9-2. 전이 지점

| 전이 | 트리거 | 함께 할 일 |
|---|---|---|
| 생성 → `WAITING` | 방 개설 | `expires_at = +10분` |
| `WAITING`/`ENDED` → `RUNNING` | 입장 | `expires_at`·`ended_at` 해제, **방장이면** 타이머 시작 |
| `RUNNING` → `ENDED` | 마지막 퇴장 | 타이머 정지, `expires_at = +30초` |
| → 소프트 삭제 | `expires_at` 경과 | 스케줄러 |

**상태 전환과 타이머 시작은 분리한다.** 방은 누가 들어와도 `RUNNING`이 되지만, 타이머는 **방장이 들어올 때만** 시작한다. 초대 링크로 방장 아닌 사람이 먼저 들어오는 경우가 있고, 타이머 시작은 원래 방장 권한(`POST /timer/start` = `findHostRoomOrThrow`)이기 때문이다. 이미 도는 타이머가 있으면 아무것도 하지 않는다(이중 시작 = `409`).

**`ENDED` 전환 경로는 두 갈래이고 둘 다 고쳐야 한다.** 한쪽만 바꾸면 나가기 방식에 따라 결과가 달라진다.

| 경로 | 위치 | 유예 |
|---|---|---|
| 명시적 나가기 (버튼) | `StudyRoomService.closeOrTransferHost()` | 없음 (즉시) |
| 끊김 · 강제 종료 · X 닫기 | `RoomPresenceTracker.sweep()` | 20초 |

타이머 정지(`POST /timer/stop`)가 `ENDED`로 보내던 기존 동작은 **제거한다.** 사람이 있는데 `ENDED`가 되면 이 모델과 어긋난다.

### 9-3. 타이밍 상수

| 대상 | 값 | 근거 |
|---|---|---|
| 이탈 유예 | 20초 | 새로고침만 살린다(결정 7). OpenVidu·MediaPipe 재로딩 포함 |
| 이탈 청소 주기 | 3초 | 유예에 맞춤. 실제 정리 20~23초 |
| `WAITING` 유지 | 10분 | 권한 허용 + 모델 로딩 + 캘리브레이션. 아래 근거 참고 |
| `ENDED` 유지 | 30초 | 빈 방을 빨리 정리. 재입장 창구는 사실상 포기 |
| 자리비움 진입 | **20초** | 잠깐 화면 밖으로 나가는 것과 구분. 구현된 값(`AWAY_AFTER_MISSING_SECONDS`)을 따른다 |

> **이탈 유예 20초와 자리비움 20초는 값만 같고 무관하다.** 앞은 "WebSocket이 끊긴 뒤 퇴장으로 볼 때까지", 뒤는 "캠에 사람이 안 잡힌 뒤 `away`로 셀 때까지"다. 한쪽을 바꿔도 다른 쪽을 따라 바꿀 이유가 없다.

**`WAITING` 유지를 2분에서 10분으로 늘린 이유.** 준비 화면에서 방장이 해야 하는 일이 권한 팝업 허용 → MediaPipe 모델 로딩 → 캘리브레이션이다. 권한 팝업을 못 찾거나 캘리브레이션을 두 번 시도하면 2분은 쉽게 넘는다. 넘기면 준비 화면에 있는 동안 스케줄러가 방을 지우고, 방장이 입장 버튼을 눌렀을 때 `404`가 난다. 안내 화면(작업 13)은 프론트 몫이라 그때까지는 그냥 깨진다. **9-5(목록에서 `WAITING` 제외)가 이미 유령 방을 사용자 눈에서 감춰 주므로, 짧은 만료로 얻을 것이 거의 없고 잃을 것은 크다.**

### 9-4. 시간을 세 갈래로 나눈다

> **일부는 이미 구현됐다.** `02c8c2c`(자리비움·졸음 분리)에서 자리비움이 들어갔다. 아래 표의
> "휴식" 줄은 방 공용 타이머(페이즈)가 붙어야 가능하므로 아직 남아 있다.

**판정 기준은 "쉬어도 되는 시간인가"다.** 페이즈를 먼저 보고, 집중 페이즈일 때만 개인 상태를 본다.

| 페이즈 | 개인 상태 | 컬럼 | 상태 |
|---|---|---|---|
| **집중** | 캠 켬 + 사람 잡힘 + 안 졺 | `focused_seconds` | ✅ 구현됨 |
| **집중** | 사람 미검출 20초↑ **또는** 졸음 | `away_seconds` | ✅ 구현됨 |
| **집중** | 캠 끔 | **아무것도 세지 않음** | ✅ 구현됨 |
| **휴식** | 캠 상태 무관 | `break_seconds` | ⏳ 페이즈 필요 |
| **휴식** | 스트레칭 중 | `break_seconds` | ⏳ 지금은 아무것도 안 셈 |

`total_study_seconds = focused + break + away`

- **미검출을 자리비움에 넣는 이유**: 캠만 켜두고 자리를 비우면 순공 시간이 계속 쌓인다. 자세 이벤트도 안 생겨 점수는 100점이 된다. 실제로 그런 기록이 있었다(`focus_score=100`).
- **졸음도 자리비움이다**: 화면 앞에 있어도 공부하는 상태가 아니다. 자세 판정과 같은 근거로 판단한다.
- **캠을 끄면 아무것도 세지 않는다**: 자리비움으로 넣으면 캠 끄고 몇 시간 방치했을 때 `total`이 그만큼 부푼다. "방에 있던 시간"이 아니라 "판정할 수 있었던 시간"만 센다.
- **휴식 중에는 캠을 꺼도 `away`가 아니다**: 쉬라고 준 시간에 쉰 것을 이탈로 세면 안 된다. 휴식 중 화상은 켜든 끄든 제약하지 않는다.
- **스트레칭도 `break`**: 어디에도 세지 않으면 `total`이 세 값의 합과 어긋난다. 공부는 아니지만 쉬어도 되는 시간이므로 휴식으로 묶는다.
- **휴식 페이즈에는 자세 판정도 멈춘다**: 자리를 뜨는 시간이라 계속 돌리면 판정 보류나 엉뚱한 나쁜 자세가 쌓인다(스트레칭 중과 같은 이유).

### 9-4-1. ⚠️ 딸린 문제 — 집중도 점수 공식을 같이 고쳐야 한다

현재 공식은 휴식을 분모에 넣는다.

```java
focusScore = focused / total * 100        // total = focused + break + away
```

`break`이 아직 0이라 드러나지 않지만, 휴식을 실제로 재기 시작하면 **규칙을 완벽히 지킨 사람이 감점된다.**

```
50분 집중 + 10분 휴식을 그대로 지킴
→ 3000 / (3000 + 600 + 0) = 83점
```

방이 정해 준 휴식을 지켰다는 이유로 깎이는 셈이다. 휴식을 분모에서 빼야 한다.

```java
focusScore = focused / (focused + away) * 100
```

이러면 자리를 비운 만큼만 깎인다(위 예시는 100점). **9-4를 구현할 때 반드시 같이 바꾼다.**

### 9-4-2. 순공 타이머는 경과 시각으로 계산한다

`setInterval`로 1초씩 더하면 **비활성 탭에서 타이머가 늦춰져** 실제보다 적게 쌓인다. 스터디룸이 팝업 창이라 뒤로 밀리기 쉬워 실제로 발생한다.

```
잘못  1초마다 elapsed += 1
맞음  (지금 시각 − 구간 시작 시각) 으로 계산
```

방 공용 타이머는 서버가 관리하므로 영향받지 않는다. **순공 타이머만 해당된다.**

### 9-5. 방 목록은 `RUNNING`만 보여준다

```
기본   status = RUNNING  ("지금 사람이 공부 중인 방")
제외   WAITING · ENDED · 삭제된 방
```

`WAITING`(최대 10분)과 `ENDED`(30초)는 **곧 바뀌거나 사라지는 과도기**다. 목록에 띄워도 들어가면 아무도 없다. "스터디방 찾아보세요"라는 화면 성격상 사람이 있는 방만 보이는 편이 맞다.

**데드락 걱정은 없다.** `WAITING`을 `RUNNING`으로 바꾸는 사람은 목록을 보고 오는 사람이 아니라 **방장**이고, 방장은 개설 직후 준비 화면 URL을 이미 들고 있다. 목록에 없어도 입장에 지장이 없다.

```
방 개설  →  WAITING (목록에 없음)
방장 입장 →  RUNNING (목록에 나타남)  →  남들이 들어옴
```

### 9-6-1. 순공시간 표시 (프론트 10번 상세)

`elapsed`는 **이번 접속에서 흐른 시간뿐**이다. 새로고침하거나 끊겼다 돌아오면 0부터 다시 센다.
서버에는 재입장 전 기록이 그대로 남아 있으므로(같은 `study_record`를 이어쓴다) 그 값을 더해야
화면과 실제 기록이 맞는다.

파생값 하나를 만들어 표시에 쓰는 곳을 통일한다.

```ts
const totalFocusedSeconds = priorFocusedSeconds + elapsed;
```

**고칠 곳이 두 군데다.** 서버 전송(3곳)은 이미 합쳐서 보내고 있어 문제가 없다.

| 위치 | 지금 | 문제 |
|---|---|---|
| 화면 타이머 | `formatDuration(elapsed)` | 새로고침하면 00:00부터 보인다 |
| **결과 화면 요약** | `focusedSeconds: elapsed` | **재입장 후 나가면 이번 접속분만 표시된다** |

두 번째가 특히 눈에 안 띈다. 서버에 저장된 값은 정상인데 "오늘 공부한 시간" 화면만 적게 나오므로,
사용자는 기록이 날아간 것으로 오해한다.
**막혀 있는 것**: 프론트 13~14는 12번(방 타이머 연동)이 있어야 한다.
**같이 해야 하는 것**: 프론트 14번을 넣는 순간 집중도 점수 공식(9-4-1)도 함께 바꿔야 한다.

### 9-6-3. 나가기 경로도 점수를 계산한다 (검증 중 발견 → 같은 브랜치에서 수정)

검증 중에 나온 문제다. 명시적 나가기(`POST /leave`)는 `left_at`만 남기고 **점수를 계산하지 않았다.**

```
[수정 전] leave 직후:  left_at=기록됨   end_reason=NULL   focus_score=NULL
```

이탈 경로(`endByDisconnect`)는 서버가 알아서 계산하는데, 나가기 경로만 프론트가 `PATCH /study-records/{id}/end`를 따로 불러 주는 것에 의존했다. 그 호출이 빠지면 점수 없는 기록이 남는다 — **결정 8의 "나가기 버튼과 동일하게 처리한다"와 어긋난다.**

`leave()`가 `endByUserExit()`을 먼저 부르게 고쳤다. 이미 종료된 세션이면 아무것도 하지 않으므로 프론트가 정상적으로 종료를 부른 경우와 결과가 같다.

| 검증 | 결과 |
|---|---|
| 프론트 `end` 없이 나가기 → 점수 계산됨 | ✅ `end_reason=USER_EXIT`, `focus_score=90.00` |
| 계산식이 맞나 (`focused 1800 / total 2000`) | ✅ `90.00` |
| 프론트 `end` 먼저 → 그 다음 나가기 | ✅ `200` (409 아님) |
| 그때 기존 점수가 덮이지 않나 | ✅ `focus_score=100.00` 유지 |

**공식은 건드리지 않았다.** 계산 시점만 맞춘 것이라 `report` 도메인(다른 담당자)이 읽는 값의 의미는 그대로다.

**예외를 잡지 않은 이유**: `leave()`와 같은 트랜잭션이라 여기서 삼켜도 커밋이 되돌아가 의미가 없다. 실패해 퇴장이 되돌아가더라도 연결이 끊기면 유예 뒤 이탈 경로가 같은 일을 다시 한다.

**같은 성격의 문제였던 강퇴는 기능째로 뺐다**(2026-08-05). `kick()`은 `end_reason=KICKED`와 퇴장 시각만 남기고
점수를 계산하지 않는 유일한 경로였다. 나가기처럼 `endWithStoredProgress`에 태울 수도 있었지만, 프론트에 한 번도
붙지 않은 기능을 위해 종료 경로를 하나 더 유지할 이유가 없었다. **지금 퇴장 경로는 나가기와 이탈 둘뿐이고 결과가 같다.**

### 9-7. 감수하기로 한 것

- `ENDED` 재입장 창구는 좁다(유예 20초 + `ENDED` 30초 = 50초). 새로고침은 유예에서 걸러지므로 실제로 쓸 일이 드물다.
- **`ENDED`에서 돌아오면 방 공용 타이머는 처음부터 시작된다.** 페이즈 진행 상태는 서버 메모리에 있어 정지 시점에 사라지고, 30초를 위해 DB에 쓸 이유는 없다. **순공시간은 깨지지 않는다** — 같은 `study_records` 행을 이어쓰기 때문이다(결정 7).
- 목록에서 본 방이 30초 뒤 사라질 수 있어, 삭제된 방으로 들어가려는 경우가 늘어난다. 프론트 8번 안내가 필요하다.
- 명시적 나가기에는 유예가 없다. 방장이 실수로 나가기를 누르면 혼자 있었을 때 방이 바로 `ENDED`가 된다. 30초 안에 URL로 돌아올 수 있으므로 복구는 가능하다.

### 이 결정이 BE 구현에 주는 뼈대
- `progress` = 측정값(focused/break/away) UPDATE. 가볍고 자주. 점수 계산 X.
- `end` = 종료 시각 확정 + `events` 집계 + 점수·비율 계산 후 study_records 확정.
- 방 페이즈 타이머 = 서버 메모리 상태 + WebSocket. (개인 타이머와 분리)
- 퇴장 경로는 자발적/이탈 둘이며 **뒷정리는 한 곳**(`leave` → `closeOrTransferHost`)으로 모은다.
- 방 상태(`status`)는 인원 수에서 파생된다. 사람 유무는 `study_records.left_at IS NULL`이 정본이고, `status`는 그것을 목록 조회에서 빠르게 거르기 위한 색인용 사본이다.
